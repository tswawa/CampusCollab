# 校园任务通（CampusTask）市场与需求研究

[English](market-research.en.md) · [总计划](../../PLAN.md) · [竞品研究](competitive-landscape.zh-CN.md) · [海外适配](international-adoption.zh-CN.md)

研究截止 2026-10-08。用户已认可继续完善、以 AGPL 开源到 GitHub，并同时提供中英文产品。当前项目仅本地开发和测试，没有学校实际采用；本文不把其他高校的使用情况当作本项目的用户或成效。

**结论：这一类软件有真实使用场景，值得继续投入。首选是院系与校园服务部门的实践任务及结项工作：明确要求、组织参与、收集材料、处理补正，并形成能核对、能交接的结果。** 已有报名、图文提交和审核产品很多，机会在于把一个具体工作办完整，同时降低配置和维护负担。

## 研究范围与证据等级

需求主样本为 10 所高校、9 个省市：辽宁、湖南、浙江、山东、四川、江苏、北京、安徽、广东。同校同项目合并计算；补充的采购、认定规则和系统问题属于采用条件证据，不混入这组统计。另见独立的八个代表竞品研究和六所海外高校研究。样本是为产品决策选择的案例，不是随机抽样，不用于估算全国市场规模、渗透率或收入。

| 证据类型 | 可以支持 | 不能直接支持 |
| --- | --- | --- |
| 学生反馈与学校回应 | 某项问题确实被提出，责任部门公开解释原因 | 全国发生率、单纯由软件引起或本项目一定能解决 |
| 已完成活动总结 | 已发生的活动、使用方式和学校报告的数量 | 独立审计、软件满意度、留存或因果节时效果 |
| 系统开放与培训报道 | 产品已进入机构流程，目标用户已被组织培训 | 受训人数等于活跃用户、长期稳定使用 |
| 操作手册与制度 | 具体流程、字段、角色、认定和交接要求 | 实际采用规模或使用体验 |
| 采购公示与成交材料 | 所注明阶段的采购理由或成交范围 | 公示等于成交、成交等于验收、合同总额等于本项目价值 |
| 源码与产品文档 | 已读路径的实现或厂商陈述的功能 | 实机可用、真实采用和相对效率 |

## 痛点与能解决的范围

| 痛点 | 证据 | 产品应完成的工作 | 不能越过的边界 |
| --- | --- | --- | --- |
| 最后才发现缺材料，反复找人补 | D09、D06 | 在发布时明确材料项，按人显示缺件，补正指出具体问题并保留前后版本 | 检查齐全不等于核验真实，不能自动决定是否应授予学时 |
| 名单、材料和最终表格要重新关联 | D04、D06、D10 | 导入已有名单，以稳定标识匹配，按最终确定版本生成表格与材料包 | 昵称或姓名不足以可靠匹配；必须适配真实模板而非随意导出 CSV |
| 参与者需要知道结果或补正进度 | D09 的延迟投诉支持改进反馈；未直接证明现有平台没有状态展示 | 个人待办、清楚的缺项和截止、通知直达、可见的处理状态 | 生成通知不等于送达，站内消息不能冒充微信或邮件触达 |
| 集体活动需要同时保留公共材料与个人记录 | D06 的统一汇总方式；属于流程需求，未证明重复上传普遍存在 | 负责人统一确认参与，公共材料一次关联，多人结果分别留记录 | 一份集体照不证明每人到场或相同时长 |
| 负责人更换后事情断档 | 组织账号与认定责任规则，见采用条件 | 可转交待办、模板、资料、运行责任并回收旧权限 | 新增一个管理员账号不能替代服务器、域名、备份和更新交接 |

这组痛点中，前两项最适合作为第一轮核心体验：最终要求前置，补正定位到项，输出时无需重新对人、找最终文件和抄主要字段。通知、交接与运维帮助它成为可持续使用的成品。

## 使用者与采用者

直接使用者是任务协调员、组织负责人和参与者；部署者是校内技术团队或负责系统的单位；正式认定者可能是学院、团委、学生处或课程管理部门；GitHub 贡献者还可能只是希望复用状态机、模板和部署方案的开发者。这些角色不必是同一个人。

开源价值包含可检查的工作流、可修改的模板、自己掌握的数据和可复现交付。AGPL 本身不创造需求；如果没有维护者，自托管就是额外负担。项目能帮助处理参与记录，不能凭系统内的角色名称取得校方正式认定权。

## 细分选择与替代路径

| 方向 | 判断 | 选择 |
| --- | --- | --- |
| 院系、后勤等部门的分散实践任务及结项 | 多校相近自研系统和具体流程，当前多人任务基础适配较好 | 首选；要求有明确负责人和维护方式 |
| 志愿活动材料与名单整理 | 需求明确，但报名工具和现有平台竞争强 | 主线子场景，重点解决最后的核对与交接 |
| 单次迎新报名 | 表单和群的启动成本很低 | 不作为独立部署的主要价值叙事 |
| 连续多日打卡 | 真实需求与成熟替代都存在，当前单份凭证模型不足 | 后续按明确需求评估，不强行扩成打卡平台 |
| 全校劳动课程和学分管理 | 多层制度、统一身份和迁移要求突出 | 提供结果接口，完整替代另行立项 |
| 正式助教、助管、勤工助学 | 聘期、资格、考勤、薪酬及审批结构不同 | 不纳入 1.0 的工资或就业管理 |
| 可复用的开源工作流实现 | 即使没有直接机构采用，状态、权限、模板和部署也可用于二次开发 | 与成品方向并行，但不能冒充真实市场成功 |

保守路径是先公开代码和运行文档，成本较低，但负责人仍需大量配置与整理。推荐路径是完成轻量自托管成品，把模板、名单、补正、结项和交接做通。激进路径是全校统一平台，集成与长期服务显著扩大，当前不选。

## 与实施计划的对应

用户认可的范围包含全部核心完善项和英文版，实施任务以 [PLAN.md](../../PLAN.md) 为准：T03 模板合同；T04 身份与数据迁移；T05 至 T08 国际化及加入；T09 名单导入；T10 至 T17 材料、审核与结果；T19 通知；T20 交接；T21 保存；T22 至 T27 运维与发布；T28 材料引用复用；T29 模板贡献；T30 有依据的外部适配。

第一轮可演示成果是一条完整流程：选择交付要求，导入或招募人员，发现缺件，定向补正，确认指定版本，生成名单、附件及核对清单。通用模板可以启动开发；机构模板须取得原件和字段解释，并将输出逐项对照后才声明兼容。

验证采用同一批虚构数据，比较原流程与新流程的重复录入、找文件、重命名、错配和人工操作时间。审核真实性的时间单列。不能在测量前宣称节省固定比例，也不把“必须先找到线下试点”作为上述产品取舍的前提。

如果现有工具配置后就能交出同样结果、每次都要重新手填主要字段、每个模板都要改核心代码，或者新增账号和上传步骤抵消收益，应调整模板或缩小产品范围。若只剩重命名压缩的收益，本地整理工具可能更适合。

## 结论与更新规则

公开资料已支持继续做一个有明确边界的双语成品：服务组织实际任务，把参与、材料和最终记录对应起来。独特价值仍需通过实现和可复核演示证明，不能由 GitHub 同名项目数量、培训规模或采购总价替代。

今后更新保留来源日期、证据类型、影响的产品决策和验证状态。学校规则或模板变化时更新对应映射；新增一个引用不自动增加一个独立市场样本。本次仅写入研究与计划，应用功能、许可证变更、部署及 GitHub 发布未执行。
